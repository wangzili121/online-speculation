# Orthrus-GLM 推理优化：成本模型与实现选择

本分析限定现有 GLM-5.3-Flash draft 定义、已有 Torch/Torch-NPU 算子和同步 eager 推理，不修改检索、Attention、KDA 或采样算法。目标是减少相同计算中的数据搬运、临时存储和主机调度开销。初始化 head 可用于实现等价性和分项计时，不能用于承诺业务加速比。

## 1. 从完整历史快照改为按需读取

一层 MLA 原先先复制全部有效 latent，再从副本中收集每行 query 命中的历史。Indexer 实际最多选中 512 个四行池，再加不足一池的尾部；未命中的 latent 不参与 Attention，因此不必先复制。

新的路径先固定 anchor 边界与页表元数据，保留目标缓存的只读引用。计算本层时，Indexer 仍扫描完整的有效历史池，再把命中的逻辑 token 索引映射到物理行，用现成 `index_select` 收集。FIA、两套 AR/draft 展开权重及联合 softmax 不变。

设：

- $L$：anchor 前的历史 token 数。
- $K$：draft query 行数；$S\le2048+L\bmod4$：每行选中的 token 数。
- $N=KS$：所有 query 收集的总行数，包含跨 query 的重复。
- $R=512$：有效 latent 维度；$P\ge R$：物理行 pitch，包含 padding。
- $b=2$：每个 BF16 元素的字节数。

### 数据搬运

若 $P=R$，忽略缓存命中和元数据，只按张量层面的读写字节数 $B$ 估算：

$$
B_{\rm snapshot}\approx2bLR+2bNR,
\qquad B_{\rm paged}\approx2bNR.
$$

若 $P>R$，现有组合先收集包含 padding 的行，再复制有效列。相应为：

$$
B_{\rm snapshot}\approx2bL(P+R)+2bNR,
\qquad B_{\rm paged}\approx2bN(P+R).
$$

此时按需读取减少搬运的条件为

$$
L>\frac{NP}{P+R}.
$$

例如 $K=8,S=2051,P=576$，分界约为 8687 个历史 token。短历史被多个 query 重复访问时，按需读取可能搬运更多数据。因此不能只凭“避免完整快照”就认定所有形状更快。

这些是张量读写模型，不是实测 HBM 流量。真实结果还受 L2 命中、随机页访问、kernel 启动、CPU 页表构造、同步和分配影响，自动选择必须以包含这些成本的计时校正。

### 额外存储

完整 GLM 有 11 层 MLA。原执行顺序在 draft 开始前同时持有各层完整 latent 快照，仅这些有效数据就占

$$
M_{\rm old,latent}=11bLR.
$$

$L=32768$ 时为 352 MiB；这不包括 AR 本身的持久 cache、Indexer 池、KDA 状态或算子 workspace。

按需路径只持有 cache 引用和自有页表元数据，本层计算时才分配选中行。即使某层选择完整快照，也延迟到该层再复制，随后释放，不再同时保留 11 层的完整副本。带 padding 的直接收集仍可能需要 $bN(P+R)$ 临时存储，不能把它称为完全零拷贝。

## 2. 只读引用成立的条件

借用 cache 不是拥有一份跨步骤快照。实现必须同时满足：

1. 只在已限定的同步、单请求、eager draft 内读取，目标模型不能同时推进或回收这些页。
2. 历史边界固定为同一个 anchor，页表元数据归本次读取所有。
3. 逻辑索引不能越过已提交前缀，包括最后一个有效页中的未提交行。
4. 收集结果拥有独立存储；draft 不写目标 latent、压缩池或 KDA 状态。
5. draft 正常返回或异常退出都释放引用；新的 metadata 捕获也使旧引用失效。

因此该改动不自动获得异步调度、并发 batch 或在线训练 replay 能力。它们需要另外设计缓存生命周期，不能直接沿用当前借用接口。

## 3. 同步与布局转换

一次 draft 的耗时可以分为：

$$
t_{\rm draft}=t_{\rm projection}+t_{\rm history}+t_{\rm attention/KDA}
+t_{\rm shared\ backbone}+t_{\rm LM\ head}+t_{\rm host}.
$$

其中主机开销还包括多次 kernel 启动、设备到主机同步和元数据构造。小块计算的算术量较小，这些固定成本不能只靠算子 FLOPS 判断。

共享 backbone 主要节省参数存储，不代表能复用主模型的全部中间计算：draft 的 MASK 输入和隐藏状态不同，MoE、norm 和投影仍要处理当前块。因此不能按“只新增少量 head 参数”来估算 draft 耗时；完整模型还应单列共享主干和 LM head 的稳态成本。

两处已落实的改动：

- 不同层引用同一个长度/位置 tensor 时跳过重复的 `torch.equal`；非同一对象仍需比较，不能删除历史一致性校验。这里没有承诺固定的耗时收益。
- 固定版本的 recurrent KDA 接收独立的 Q/K/V token/head stride。K=1/2/8、8/64 heads 的输出和逐位置状态与连续化调用逐元素相同，已移除这三次复制；K=8 的局部调用耗时实测降低约 14%。

临时状态或设备元数据复用也有潜力，但需明确有效长度、重置位置和缓冲区所有权，避免上一请求或反向 KDA 的状态泄漏。它不是可以无条件增加的全局缓存。

### 不能直接替换的 Indexer 入口

固定 0.30 镜像的 `ops/triton/glm5_next_lightning_indexer.py` 先计算 $\bar q_i=\sum_h\omega_{ih}q_{ih}$，再用 $\bar q_i^\top\kappa_r$ 打分。当前 draft 和所参考的 PyPTO `indexer_score` 则使用 $\sum_h\omega_{ih}\operatorname{ReLU}(q_{ih}^\top\kappa_r)$。ReLU 在 head 合并之前，不能移出求和。

例如两个 head 的 query 分别为 $(1,0)$、$(-1,1)$，权重均为 1；历史 key 为 $A=(1,0)$、$B=(0.6,0.6)$。逐 head ReLU 给 A/B 打分 1/0.6，先合并 query 则为 0/0.6，排序相反。因此该原生入口不能作为当前公式的等价替换；其完整 AR wrapper 还会更新池和尾部 cache，也不能直接作为只读 draft 入口调用。

本轮保持主模型原生路径和 draft 检索定义各自不变。若未来采用其他检索定义，必须先明确 head 的训练契约；不能将其包装成单纯的算子调用优化。PyPTO 核对版本为 `2aef4534f8769d8ce8d49d9dde7e5aeebc472197`，这里不据两个实现的差异判定哪一个主模型实现有缺陷。

## 4. 后续优先级

| 方向 | 理由与限制 |
| --- | --- |
| 按需读取 latent、延迟短历史快照 | 减少长上下文的数据量和多层快照驻留；先比较短/长历史、不同 pitch 和 K。 |
| 减少重复同步与布局复制 | 固定开销对短块更明显；保留非别名 metadata 的检查。 |
| 页表传递与物理索引构造 | 读取总耗时仍随 L 明显增长。先分项测 D2H、CPU 映射与设备收集，再决定是否保留设备端页表或复用请求内映射；必须保留版本、边界和释放约束，不能缓存上一轮可变页表。 |
| Indexer 直接扫描分页池 | 当前仍复制完整池，且 FP32 打分有中间张量。同版原生 Triton 入口与当前逐 head ReLU 公式不同，不能直接替换；其他候选也须核对公式、cache ABI、缩放和近似并列分数下的选择。 |
| 图模式、并发与整模型 TP8 | 属于后续执行能力与验收，不是简单换一个 Attention 算子。应依据完整模型的稳态 profiling 排序。 |

优化整个 draft 的上界还受未改动部分约束。若某项占原耗时比例为 $f$，局部加速为 $r$，整体加速至多为 $1/[(1-f)+f/r]$。因此局部读取快十倍不代表整个模型快十倍；模型初始化、缓存审计和 head 保存也不应混入稳态性能结论。

例如某项若只占 20%，即使耗时减半，整轮理论上也仅约快 11%；这是假设示例，不是当前模型的 profiling 结果。下一轮应先测出各项的真实占比，再决定是继续减少历史搬运，还是处理调度与共享主干调用开销。

## 5. 实测与验收

实现位于 `glm53_history.py`，原有完整快照与新按需读取均保留，提供 `auto / snapshot / paged` 三种读取模式，head 参数和格式不变。计时脚本为 `scripts/benchmark_glm53_selective_history.py`；比较包含页表获取、索引映射、分配和布局转换，不只计核心 gather。

回归覆盖跨页/子页、重复索引、页末未提交位置、页表后续变化、引用失效、异常释放和目标 cache 不变。真实源权重五层、单卡 TP1/K=8 通过七个强制按页读取阶段和两个自动模式交叉重载阶段；六个 greedy draft/reload 阶段均逐 token 对齐，两种 head 哈希不变，合计 444 次缓存审计通过。读取计数确认两条路径实际执行，不只检查服务有输出。这不是完整 45 层 TP8 或采样分布验收。

16 组实测显示：包含主机与映射开销后，32K 历史的两种读取均约 3.9 ms，按需路径并未带来可靠延迟收益；K=8、pitch=576 的峰值分配则由 68.26 降至 34.32 MiB。2055-token 的相同几何中，按需路径反而由 0.70 升至 0.83 ms、18.03 升至 34.30 MiB。因此自动模式采用 **L≥32768 且 L≥KS** 的保守规则，其余形状延迟生成快照；可强制指定两种模式进行对照。这个分界是当前测量选择，不是由搬运公式推导出的普适阈值。

KDA 布局比较中，8/64 heads 分别为 524→451 μs、495→423 μs。它只说明这一段现有算子的调用更合适，不等于整轮 draft 或服务获得同等比例提升。原始结果与测试索引归档于 `validation/glm53/selective-20261103/`。
