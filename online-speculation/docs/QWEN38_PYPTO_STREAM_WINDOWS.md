# 两卡在线更新的请求窗口对照

OneServing 的调度器已经能在一个请求结束后补入新请求。两题一组、等两题都结束再提交下一组的评测方式，却会让先结束的 slot 等待另一题。本实验增大提交窗口，检查这一空档对固定起草和持续更新的影响。

`--stream-window` 控制一次入队的请求数，默认仍为 2。设为 4 时，先提交四题，调度器同时执行的上限仍为 **2**；TP2、物理卡数、目标模型、输出预算和初始 head 均保持一致。AR、固定起草、持续在线采用相同窗口和题目顺序，在六种方法顺序间轮换。窗口之间结清当前工作，在线优化器和权重版本跨窗口保留。

这是一种新的请求到达方式，不能与旧两题协议的吞吐直接相减，作为单独的算子或调度器加速。收益仍须用本次同条件 AR 和固定组计算；最终冻结 head 的原题重跑另存。

## 实现与检查

- `benchmark_qwen38_oneserving_tp2_online.py`：统一构造提交窗口，先入队再等待；逐窗口保存请求序号、输出 token 数、耗时及更新状态。
- `online_study_metrics.matched_request_timelines`：三个方法必须覆盖全部相同请求、相同窗口；缺题、重复、不同分组、零输出或非有限耗时均拒绝验收。
- `--audit-admission`：仅用于诊断，记录真实活跃请求和补位事件；带此标记的运行不参与性能验收。

485 项 CPU 回归通过。真实 27B、两张 A2 的默认两题回归完成 8 次更新，loss、梯度范数、裁剪、监督行数和最终两个 rank 的权重哈希均与保留版本相同。

四题窗口的独立短检查使用原探索流前 8 道 Pseudo2code，完成 24 次更新。greedy 输出与 AR 相同，教师回放满足既有误差门槛，发布 head 精确导出。包含控制组、在线及冻结回放在内的调度轨迹中，最大活跃数为 2，记录到 34 次在另一请求尚未结束时补入新请求，最终无活跃请求遗留。该诊断含回放检查，耗时不作为收益结果。

完整 56 题的 KL 与 `log_overlap` 对照分别运行，关闭调度追踪和额外回放诊断。全部反馈、训练、发布和末尾等待计入，完整结果出来前不宣布达标。
