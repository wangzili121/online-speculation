# 在固定上下文内增加输出预算

默认的固定输出上限保持不变。新增 `--clip-output-to-context`：先按 native engine 相同的 chat template 计算完整输入长度，再为每题分配

$$
B_i=\min(T, C-N_i),
$$

其中 $T$ 为 `--tokens`，$C$ 为总上下文上限，$N_i$ 为含生成前缀的输入 token 数。所有题目和完整输入均保留；AR、初始固定起草、持续在线、最终 head 重跑与留出评测共用同一预算映射。计时内仍调用原提交、tokenization 和生成路径，在线反馈及更新开销照常计入。

报告记录每题输入长度、分配预算及各窗口的实际输出，EOS 仍可提前结束；吞吐按实际 token / 完整耗时计算。该选项用于检验较长生成是否能提供更多反馈和摊薄 prefill 开销，不与旧短输出结果直接混作同条件增益。

```text
--max-model-len 1024 --tokens 512 --clip-output-to-context
```

现有 LongProc 30 题的总最大输出容量由 3,840 增至 13,907 token；SPoC 派生 64 题由 12,288 增至 32,271 token。这些是 tokenizer 计算的预算上限，不是实际生成量或速度结论。没有按答案、输出或性能挑题。

592 项 CPU 回归通过，包含逐题预算、实际 chat template、超限拒绝、提交前校验和默认记录格式。真实 tokenizer 的预算核对通过。旧题的双卡边界诊断已通过：两条输入分别为 992 / 1,000 token，统一请求 512 token、实际分配 32 / 24，均覆盖 1,024 总长度；AR、固定、在线及最终 head 重跑输出一致，完成 3 次实际更新和发布，实际权重分片与导出一致。诊断忽略 EOS 以覆盖边界，不参与性能验收；后续完整探索使用自然 EOS。

模型及 PyPTO kernel 沿用已验证实现。新性能配方要在功能检查通过后重新完整测量并冻结，GSM8K 已完成的冻结确认及代码生成的原配方结果不改写。原始 CPU、准备阶段失败与修正、预算清单及实机诊断保存在 `validation/pypto-qwen38/online-datasets-20261119/context273/budget303/`。
