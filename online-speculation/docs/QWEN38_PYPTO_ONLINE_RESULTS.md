# Qwen3.8 Orthrus / PyPTO 持续在线更新结果

同两张 Ascend A2、TP2、相同基模和起点 head 下，GSM8K 与 SPoC 代码生成流均完成三次独立重置确认：持续在线吞吐每次及合并都超过 AR、固定起草各 5%。三卡独立学习器单独记录；其 GSM8K 新题确认仍在进行，整体工作尚未验收完成。

## 比较方式

四种模式分别是普通 AR、固定起点 head、从首条请求开始按间隔持续更新，以及流结束后冻结实际发布 head 再推理。固定起点是已有预热的 **step128**，每次确认重新加载同一权重并初始化 Adam。最终冻结推理包含同题重跑和另行留出的 32 题；两者用于观察学到的 head，不能替代持续更新全流收益。

测量采用 PyPTO/OneServing 引擎路径，普通 AR 与 Orthrus 使用相同的主模型计算实现，各模式均关闭跨请求 prefix cache。主模型和 draft 均为 TP2，greedy，块宽 K8、每轮最多 7 个候选，双请求窗口，每题最多输出 192 token，遇 EOS 停止。GSM8K 的固定服务上下文为 512、训练图为 32 行；SPoC 分别为 1024、16 行。训练图的物理行数与起草的逻辑 K 不同，两组双请求起草均采用 16 个物理行。基模、生成配置、物理卡和 TP 在同一次对照内一致。双卡学习器与 rank0 共卡；三卡组额外保留第三张学习卡，三卡组的各模式均按三张物理卡计资源。

在线全流计时包含请求生成、教师反馈、反向、Adam、权重发布及尾部等待。模型冷启动/编译、实验结束后的 checkpoint 导出和单独冻结评测另计；本报告是引擎请求流计时。三次重排同一题池、独立恢复学习状态，合并吞吐按总 token / 总秒数计算。
