# 完整双卡请求流的执行量与在线开销

只分析已完成并通过原始记录审核的实验：GSM8K三次、原LongProc三次、SPoC补充流前两次。SPoC第三次仍在运行，中途数字不进入本表。这里没有重新运行模型或更改配方。

平均接受数为每个draft轮次接受的候选token数，不包括主模型补出的token；它不是“接受比例”。下表比较同一次实验的初始固定起草与持续在线更新。

| 请求流 /顺序种子 | 平均接受数：固定→在线 | draft轮次数减少 | 验证调用次数减少 | 反馈+更新+上传占在线全流 | 在线相对固定 |
| --- | ---: | ---: | ---: | ---: | ---: |
| GSM8K /743 | 1.267→1.499 | 9.27% | 8.75% | 1.804% | +6.27% |
| GSM8K /744 | 1.267→1.507 | 9.56% | 9.14% | 1.728% | +6.87% |
| GSM8K /745 | 1.267→1.491 | 9.00% | 8.28% | 1.967% | +6.13% |
| LongProc /743 | 1.257→1.494 | 9.54% | 8.94% | 2.206% | +2.22% |
| LongProc /744 | 1.255→1.448 | 7.90% | 7.14% | 2.207% | +3.02% |
| LongProc /745 | 1.257→1.441 | 7.51% | 6.85% | 1.962% | +3.94% |
| SPoC /743 | 1.306→1.814 | 18.09% | 14.05% | 0.945% | +10.72% |
| SPoC /744 | 1.305→1.763 | 16.58% | 13.93% | 0.992% | +9.51% |

在线学习后，各组都接受了更长的前缀，完成相同输出所需的起草和验证调用随之减少。SPoC前两次的执行量降幅较大，在线开销约占1%；原LongProc也改善了接受数，但相对固定起草的全流收益仍不足5%。这说明接受数改善不能单独当作吞吐达标，也不能把原LongProc的结果解释为“完全没有学到”。

这些是各自完整流的观测值，不是跨数据集的单因素消融。GSM8K、LongProc、SPoC的题目、长度、流大小和损失配置不同，不能据此断言某个数据集或流长度独自造成收益差异。

`completed-work-counters.json` 保存逐组原始SHA256、输出token数、墙钟时间、接受数、执行次数及分阶段计时。`summarize.py` 先匹配已审核原始文件的哈希，只提取完整两卡、rank0共卡、greedy一致的记录。第三次SPoC确认收齐后，重新执行即可纳入，不读取中途进度：

```bash
python3 summarize.py --output completed-work-counters.json
```

开销按 `feedback_ns + update_ns + publish_upload_ns` 计算；回读与TP整理已经包含在 `update_ns` 内，不能再加 `publish_ns`。这里只报告原有计时，不将它们视作纯kernel时间，不通过扣减开销估算虚构的吞吐。AR路径没有记录同名验证调用计数，其零值不表示主模型没有执行。三卡后台更新存在时间重叠，不纳入本表。
