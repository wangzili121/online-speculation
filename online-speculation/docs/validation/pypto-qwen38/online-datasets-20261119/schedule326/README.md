# 更新事件与计时复核

本检查读取已经完成、正常退出的原始报告，对照实际事件核对持续更新，补充部署参数和全流账目检查。它不启动模型，不派发题目，也不替代数据隔离、源码、实际权重分片或性能验收。

逐次检查更新轮次是否跨过应有间隔，是否按 warmup 执行学习率，是否每4次更新发布一次，以及最后的优化器版本、服务版本和导出 head 是否对应。验证行每批可能为1或2，因此跨过整倍数时允许最多一行偏差；不会错误地要求所有轮次严格等于16的倍数。所有更新和发布计时必须与全流计数逐项守恒；参数读取、TP整理已在更新计时内，不重复计入。

已对 GSM8K 三次两卡确认、LongProc 三次未达标确认、C机两组高频探索和B机两组三卡辅助流共10份完整报告执行检查，均通过。这证明其更新计划和计时记录一致，不会改变 LongProc 未达性能门槛的结论。三卡后台训练的工作耗时可能与生成重叠，只单独记录，不把其工作耗时占比当成延迟占比。

冻结实现中，`restore()` 恢复初始 master 并清空 Adam 状态；`prepare_batch()` 在常驻的初始 /更新 bank 间切换。固定与AR组通过 `evaluation_paused` 禁用反馈和更新，逐请求比较学习器快照并要求学习计数为零。在线组的优化器及反馈窗口跨请求保留。此路径与逐事件检查结合，避免只根据配置字符串认定“固定组冻结”“持续组在更新”。

运行：

```bash
python3 audit_schedule.py REPORT.json --stride 64 --output AUDIT.json
```

`completed-reports-audit.json` 绑定10份报告的SHA256。`watch_completed.py --validation-root ... --artifacts ...` 等待已派发的SPoC三次确认和C机同机频率对照完成主审核后，再进行同样的只读检查；不会重启、调参或重跑模型。
