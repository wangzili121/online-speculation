# 同步独立学习卡的 GSM8K 探索

该组检查现有同步学习器能否减少三卡在线流的额外开销。主模型和 draft 仍为 TP2，学习器使用第三张卡；AR、固定起草和持续在线使用同样三张卡。三组按每两题交错，并轮换六种执行顺序，以减少整段先后运行的时间漂移。同步反向、Adam 和发布会阻塞当前在线组，这些时间全部计入。

使用已经测过的 384 道探索题和旧的 16 道留出题，不使用新确认题。模型计算源码、基模和 step128 head 保持冻结，每次重新初始化 Adam。更新配方为 last-1、TV、学习率 1e-5、前 8 步预热，前 256 次更新每 16 轮一次、随后每 128 轮持续更新，每 4 步发布。greedy、K8、7 个候选及教师位置、每题最多 192 token，遇 EOS 停止。

两台机器各先通过 `sync344` 的旧输入功能审核，包括完整计时、逐请求 greedy、控制组不更新、反馈 replay、物理 worker 绑定以及实际发布权重的哈希，才派发本机完整探索。启动器只占空闲卡，保留 96 GiB 主机内存预检；不修改原确认用例，也不按性能结果自动重试。

`protocol.json` 和 `queue-*.json` 固定配方及资产哈希。`watch.py` 监督功能门槛、派发旧题探索并归档结果，物理卡及 worker 记录在各 tag 的 `resources.json`；结果、日志、源码和审核记录按 tag 保存。该监督器不会分配或启动新的确认集。只有完整探索同时超过 AR 和固定起草各 5%，才有资格冻结新方案，再用未用题做三次确认；原三卡负结果照常保留。
