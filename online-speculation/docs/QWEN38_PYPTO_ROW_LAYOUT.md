# 双请求 draft 的紧凑计算布局

当逻辑块长为 8（anchor 加 7 个候选）时，双请求仍按每请求 32 行执行投影和共享 backbone。Attention 的可见范围已经正确限制，但矩阵核仍处理 64 行，其中大部分不会参与验证。`--compact-paired-rows` 将每请求前 16 行压紧，复用主模型已有的 M32 矩阵核处理两个请求；不修改 Attention mask、候选数、权重或主模型配置。

| 项目 | 默认布局 | 可选紧凑布局 |
| --- | --- | --- |
| 双请求矩阵计算 | 32 + 32 行，M64 | 16 + 16 行，M32 |
| 每请求有效块 | 配置的逻辑 K | 同一逻辑 K，须不超过 16 |
| 外部输入、logits 和反馈 | 每请求 32 行 | 保持每请求 32 行 |
| 单请求、K 大于 16 | 原实现 | 仍使用原实现 |

入口压紧 hidden 和 RoPE。层间投影、GDN、双向 Attention 和共享 MLP 使用紧凑行号；请求 slot、历史边界及缓存容量保持不变。层组结束时将 hidden 和最终 logits 放回原位置，未计算的尾行写零。训练采集也恢复为原来的 32 行接口，只改变无效尾行，不缩短有效监督。参数加载、优化器和发布协议不变。

代码入口：`oneserving_tp2_programs.py`；行布局：`tp2_row_layout.py`；GDN 行跨度：`tp2_gdn_convolution.py` / `tp2_gdn_rows.py`。真实模型可用 `--audit-row-layout` 对同一轮 draft 额外运行默认布局，比较有效候选的完整词表 logits。该诊断模式不参与性能结论。

## 验证

固定版本环境下，525 项 CPU 测试与真实形状的 draft / 训练入口编译通过。真实 27B、两张 A2、TP2 的默认布局回归完成八次更新，loss、梯度范数、裁剪、学习率和监督轨迹与保留版本逐值相同，最终两个发布 shard 的 SHA256 一致；greedy 与 AR 一致。

独立单卡检查覆盖压紧、恢复、第二个请求的反馈，以及非零历史下的卷积和 GDN 递推。有效行与原布局逐位一致，尾行正确清零，输入和历史状态未被修改；递推也通过独立 Torch 参考检查。组件测试第一次在测试脚本编译时因元组赋值语法退出，改为独立赋值后通过；产品源码未因此更改。更早两次完整入口编译的形状推导失败也保留在证据中。

紧凑布局的真实整模型 logits、教师回放、更新及发布验证正在执行；通过后才运行无额外诊断的完整流计时。固定起草与在线组必须同时使用相同布局，AR 保持相同主模型配置。**当前开关默认关闭，尚无紧凑布局的吞吐收益结论。** K16 的整模型检查另行记录，不从 K8 结果外推。

源码快照、完整编译记录、组件检查及默认路径回归见 `validation/pypto-qwen38/online-datasets-20261119/rows233/`。
